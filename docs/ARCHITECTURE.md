# 架构说明

## 组件分层

```
┌───────────────────────────────────────────────┐
│ Cloudflare（可选）                             │
│  Brotli / HTTP3 / 边缘缓存 / 优选 IP           │
└───────────────────┬───────────────────────────┘
                    │ 回源
┌───────────────────▼───────────────────────────┐
│ OpenLiteSpeed（单进程组，全站共享）             │
│  listener 80/443（域名模式） + 8100+（端口模式）│
│  vhost × N，各自 docRoot / 安全头 / rewrite     │
└───────────────────┬───────────────────────────┘
                    │ lsapi
┌───────────────────▼───────────────────────────┐
│ LSPHP 8.3（按需拉起工作进程）                   │
│  opcache + APCu（对象缓存，进程内共享段）        │
└───────────────────┬───────────────────────────┘
                    │ PDO
┌───────────────────▼───────────────────────────┐
│ SQLite 库 × N（/var/www/db/<slug>.sqlite）      │
└───────────────────────────────────────────────┘
```

三层缓存各司其职，不重叠：

| 层 | 组件 | 作用范围 | 失效方式 |
|---|---|---|---|
| HTTP 整页 | LSCache（OLS 模块 + 插件） | 匿名访客的完整 HTML | TTL / purge / 内容更新 |
| PHP 对象 | APCu | 单站点进程内对象 | 进程重启 / `wp cache flush` |
| 数据库 | SQLite | 持久化 | — |

## 单站隔离边界

| 资源 | 共享 | 独立 |
|---|---|---|
| WP 核心（wp-admin/wp-includes） | ✅ 硬链接，101MB 一份 | |
| 插件 / 主题目录 | ✅ 硬链接（`HARDLINK_PLUGINS`） | |
| wp-content/uploads | | ✅ |
| SQLite 数据库 | | ✅ |
| 缓存盐 `WP_CACHE_KEY_SALT` | | ✅ |
| LSCache / APCu 命名空间 | | ✅（盐隔离） |
| OLS vhost / 日志 / 安全头 | | ✅ |
| PHP 进程池 | ✅ | |

硬链接的共享是**只读语义**：某站升级插件时，WP 会重建目录和文件（新 inode），其他站不受影响；反过来也成立。因此**不要**在共享核心目录里做原地修改（例如直接 `wp core update` 到 `wp-core/`），否则会同时影响所有站 —— `upgrade` 命令按站执行，升级核心时每站各自替换文件。

## 请求路径

1. 请求进入 listener（80/443 或 8100+），按 `map <domain> *` 命中 vhost；
2. OLS 查 LSCache：命中则直接返回 HTML，**不进入 PHP**（这是低配机能带多站的关键）；
3. 未命中则转 LSPHP：`wp-load.php` → SQLite drop-in → 渲染；
4. 响应带回 `X-LiteSpeed-Cache-Control`，OLS 存缓存；
5. APCu 在 PHP 进程内缓存对象/选项，减少 SQLite 查询。

## 状态模型

工具的唯一事实来源是 `/etc/wp-cluster/sites/<domain>.env`：

```
DOMAIN / MODE / PORT / URL / TITLE
ADMIN_USER / ADMIN_PASS / ADMIN_EMAIL
SITE_DIR / DB_PATH
INDEX / SSL / PHP_MEMORY / WP_VERSION / CREATED_AT
```

- 所有读命令（list/info/status/health）只读注册表 + 现场探测，不改状态；
- 所有写命令先改注册表，再改现场（或反之），失败时回滚现场、不写注册表；
- `import` 用于把"现场有、注册表没有"的历史站点纳入管理；
- 注册表与现场漂移时，`doctor` 与 `list --check` 会暴露。

## 一致性保障

| 风险 | 措施 |
|---|---|
| 并发执行写坏配置 | 全局 `flock`（只读命令不取锁） |
| 改坏 OLS 配置 | 事务：备份 → 修改 → `lshttpd -t` → 失败回滚 |
| 建站中途失败 | 回滚目录/库/vhost + 恢复配置快照，注册表不落盘 |
| SQLite 属主错误 | 每次 wp-cli 写操作后自动修属主（含 `-wal/-shm`） |
| 备份不一致 | `VACUUM INTO` 快照，而非热拷贝数据库文件 |
| 备份损坏 | 打包后 `gzip -t`，恢复时校验 `SHA256SUMS` + 路径穿越 |
| 证书申请触发限流 | 先做 HTTP-01 真实探测，探测失败直接退出 |

## 资源模型

单核机器上，瓶颈顺序是：**PHP 工作进程数 > 内存 > 磁盘 IO**。

- 稳态（缓存命中）：只消耗 OLS 的 21MB + 少量 PHP，站数增加几乎无感；
- 峰值（缓存大面积 miss）：每个 LSPHP 进程 40–60MB，1.4G 机器建议同时不超过 6–8 个；
- 因此正确的优化顺序是：先提高缓存命中率，再考虑加内存/加核。
