# Docker vs 原生：为什么这套站群不用容器

## 结论先行

| 场景 | 选择 |
|---|---|
| 单机、5–50 个小站、内存 ≤ 4G、追求单站成本 | **原生（本方案）** |
| 多机编排、需要镜像级回滚、多人协作、合规隔离 | **Docker / K8s** |
| 只要 1–2 个站、需要一键迁移到任意云 | Docker 也够用，差异不痛 |

本站群的实际负载（1 核 / 1.4G / 1G swap / 7 个站点）处在上表第一行，所以选原生。

---

## 实测数据（本机，2026-11-15）

原生栈空闲状态：

| 指标 | 数值 |
|---|---|
| OpenLiteSpeed 进程 | 3 个，RSS 合计 **21MB** |
| DB 常驻进程 | **无**（SQLite 在 PHP 进程内，按需） |
| 对象缓存 | APCu 共享内存 128MB（懒分配，不预占 RSS） |
| 7 个站点磁盘合计 | **1.0–1.1G**，其中共享核心 101MB、SQLite 15MB、uploads 61MB |
| 新增 1 个站点 | 独占 **约 0.5MB**（数据库）+ 硬链接核心 0 增量 |
| LSPHP 进程 | 按需拉起，空闲 3–4 个 |

容器栈的同等配置（Docker + MariaDB + Redis + OLS 容器）参考公开基准：

| 组件 | 常驻内存（典型） | 磁盘 |
|---|---|---|
| dockerd + containerd | 80–150MB | ~300MB |
| MariaDB 容器（buffer pool 128M） | 120–200MB | ~400MB 镜像 |
| Redis 容器 | 10–30MB | ~40MB |
| OLS + PHP 容器 | 30–50MB | ~400MB 镜像 |
| **合计（不含 PHP 工作进程）** | **240–430MB** | **~1.1GB 镜像层** |

> 上表为本机实测（原生）与公开基准（容器）的对照，未在本机安装 Docker 以免挤占内存影响对照公平性。

在 1.4G 内存的机器上，容器方案光固定开销就吃掉 1/4 到 1/3，留给 PHP 工作进程的余量明显变少；而本站群页面的内存峰值正是靠 PHP 进程吃下的（压测时 LSPHP 曾涨到 8 个进程）。

---

## 磁盘：硬链接是决定性差异

原生方案里 `wp-admin` + `wp-includes`（101MB）用 `cp -al` 硬链接到每个站点，**全机只存一份 inode**，新建站几乎不增加磁盘。

容器方案做不到这一点：

- 每个容器有自己的镜像层，WP 核心要么进镜像（每镜像一份），要么挂卷；
- 若用同一卷 bind mount 给多个容器，就放弃了容器最大的价值（隔离），等于绕回共享目录；
- 结果通常是每站 50–60MB 起步，10 个站就多出 500MB+。

对一个"要铺几十个站"的场景，这个差异会持续放大。

---

## 容器真正赢的地方

| 维度 | 说明 |
|---|---|
| 可复现 | 镜像即环境，换机器 `compose up` 即可 |
| 回滚 | 镜像 tag 回滚，比改配置回滚更硬 |
| 隔离 | 单站被拿下不影响其他站（本方案共享 OLS 进程） |
| 多版本 | 不同站可以跑不同 PHP 版本，本方案全局一个 LSPHP |
| 团队 | 配置即代码，天然进 Git |

如果这些是你的硬需求，容器更合适。本方案的取舍是：**用工程纪律（校验、快照、回滚、自检）替代容器提供的部分保障**。

---

## 兼容性风险怎么兜

"不用 Docker 兼容性差"这个担心是合理的，本方案用四层兜底：

1. **`doctor` 前置自检**：OS 版本、OLS/lsws 服务、LSPHP 扩展（pdo_sqlite/sqlite3/apcu/opcache/mbstring/curl）、wp-cli、模板站、配置语法、磁盘、Swap、目录权限、依赖命令，任一失败直接拦住，不带病部署。
2. **配置改动事务化**：改 OLS 配置前自动备份，改完 `lshttpd -t` 校验，失败自动回滚；建站失败还会回滚目录/数据库/vhost 并恢复配置快照。
3. **`--dry-run`**：所有变更命令可先打印计划，确认无误再落盘。
4. **版本锁定**：README 声明仅支持 Debian 12/13、Ubuntu 22.04/24.04；`self-update` 有语法与特征串双重校验，坏包进不来。

代价是：换到 CentOS/Alpine 需要自己适配包名与路径（`conf/wp-cluster.conf` 里路径都可覆盖）。

---

## 如果哪天真要上容器

迁移路径是清晰的，因为本方案已经把"数据"和"代码"分离：

1. 每站 `wp-cluster backup <domain>` → 得到 `database.sqlite` + `site-files.tar.gz`；
2. 容器侧起 MariaDB，把 SQLite 用官方 `sqlite-database-integration` 的导出工具转 MySQL；
3. 代码侧打成镜像，`wp-content/uploads` 挂卷；
4. 域名逐个切流。

所以当前选择不是"锁死"，而是"先把单机成本压到最低"。
